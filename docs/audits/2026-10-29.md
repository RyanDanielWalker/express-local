## Findings

1. **A drill's ending screen acts on the selected line, not the drill.** 1.0 (a bug a visitor would hit). Medium. From reading the code. `App.tsx:374-385` passes the selected line and `board()` to `Derailed` whatever the mode, and `App.tsx:367` does the same for "Ride again" on `Results`. Run out of hearts on a cram drill with a fresh save, and "Service suspended" shows Push & Pop Shuttle's field guide, and "Try again" starts a Push & Pop Shuttle ride. `board()` (`App.tsx:116`) does not check the line is unlocked, so after opening a locked line by URL (`/react/state` on a fresh save), a drill's "Ride again" plays that locked line.
2. **A drill that derails saves its answers under the wrong line.** 1.0, with finding 1: the same function, one line. Confirmed. `App.tsx:169` keys each answer by `question.from ?? LINES[current].id`, and drill questions from quiz lines have no `from`. A missed Wiring Yard question was saved as `render:13iizaw` instead of `di:13iizaw`, so it never shows as shaky. `onCramDone` (`App.tsx:264`) already falls back to `drillOwner`; `onDerail` does not.
3. **The results screen says a shaky question needs two right answers in a row.** Parked, but small enough to fold into finding 1. Confirmed. `Results.tsx:130` says so; `recordAnswers()` cancels one miss per right answer (`questions.ts:260`), so one miss and one right answer clears it. The Today band says it right. The comment at `questions.ts:259` and the test name at `engine.test.ts:432` repeat the wrong version, though the test body proves the right one.
4. **Riding a line every day can keep it from ever being due.** Parked, a design question. Confirmed. `finishTrip()` (`progression.ts:481-489`) only moves a box on a due ride, but every ride resets `due` to now plus the box's gap. Clear a line at 8pm and ride it at 7pm each following day: after 10 rides it is still in box 0, with 0 reviews counted. Comparing by calendar day, or leaving `due` alone on an early ride, would fix it.
5. **Six algorithm games show their helper panels on Rush Hour.** Parked (algorithms are parked). Medium. BubbleSort, HashTable, MergeSort, QuickSort, StackQueue and TwoPointers never read `api.assist`, so BubbleSort's "Remember it" panel shows the hook on Rush Hour (`BubbleSort.tsx:134`). Breaks a `CLAUDE.md` rule, and makes the README's "Rush Hour turns the helper panels off" untrue for those lines.
6. **Three games find their own line by position.** Parked. Small. `LINES[0]`, `LINES[3]` and `LINES[4]` in `StackQueue.tsx:208`, `BinarySearch.tsx:175` and `BubbleSort.tsx:136`. Adding an algorithm line earlier in the list would show the wrong hook. The games already get `line` as a prop.
7. **The algorithm code check moves on after 2.2 seconds, and has no number keys.** Parked. Small. `Quiz.tsx:31`. The README says "You advance, not a timer" and "Number keys pick an option"; `QuizGame.tsx:13-15` explains why the old auto-advance was removed.
8. **Nothing tests `App.tsx`'s wiring.** On Parked already, as part of "Split `App.tsx` into `useRun` and `useDrills`". Findings 1 and 2 both live there, which is a reason to do that split.

Noted, no action needed: the streak logic is copied in `progression.ts:320`, `361` and `465`. The Out Loud badge promises "without reading from the screen", which the app cannot check. Misses on algorithm code checks never become shaky, because `shakyQuestions()` only reads `line.questions`.

## Interview questions

1. **How does readiness work?** `progression.ts:166-185`. A 0 to 1 score per line from the tier cleared, how far along its review schedule it is, and the share of its questions answered without a miss. It drops as a review goes overdue, to half at most, so it shows what you would recall today. The weights (0.45, 0.2, 0.2, 0.15) have no recorded reason.
2. **How do reviews get scheduled?** `progression.ts:480-489`, gaps in `BOX_DAYS` at `save.ts:6`. Each line sits in a Leitner box, a step on a 1, 3, 7, 14, 30 day schedule. An on-time review with at most one mistake moves it up a box, a rougher one moves it down. Follow-up to expect: finding 4.
3. **Why is "done" a test?** `src/data/bar.ts`, [ADR 0005](../adr/0005-the-bar-as-a-test-ratchet.md). The bar turns "this line is finished" into checks the test suite runs. Once a division is in `FINISHED`, a line that slips fails CI.
4. **How does a save survive a new field, or a broken code?** `save.ts:35-72`, [ADR 0015](../adr/0015-repair-damaged-saves.md). `migrate()` rebuilds the save field by field: a wrong type gets its default, an unreadable entry is dropped, so a bad code never crashes the app. A new field needs a default in `emptySave()` and a line in `migrate()`, or it is lost on the next load.
5. **Why are the algorithm games state machines?** `src/algorithms/graph.ts:83`, rule 1 in [ARCHITECTURE.md](../ARCHITECTURE.md). The rules are plain functions that take the state and a move and return the next state. That makes them testable without a browser: the tests play each game perfectly and compare against a reference.
6. **How do you know the content is right?** [ADR 0006](../adr/0006-prove-claims-by-running-them.md), `probes/`. Every claim, including why each wrong option is wrong, is run as real code: the compiler, React in jsdom, or a small Nest app. A separate agent that did not write it then checks it again.
7. **Why your own router?** `useUrl.ts:34-45`, [ADR 0019](../adr/0019-a-small-router-of-our-own.md). Five URL shapes did not justify a library. Each history entry remembers the page it came from, so leaving a ride steps back instead of pushing, and Back never lands on a ride that is gone.
