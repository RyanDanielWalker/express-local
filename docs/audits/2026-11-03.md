## Findings

Ranked by how much they matter now that 1.0 is tagged.

1. **Riding a line before it is due can keep it from ever moving up a box.** On Parked. Small to medium. Confirmed by the first audit, and the code has not changed. `finishTrip()` moves the box only on a due ride (`progression.ts:481-487`), but every ride resets `due` (`progression.ts:489`). Clear a line at 8pm, then ride it at 7pm each day after: it stays in box 0, and no review is ever counted. The app's own advice can set this off, from reading the code. The Daily Ride is picked from every unlocked line (`progression.ts:125`). The Today band shows it whenever it is not due (`today.ts:51-56`). So following the Daily Ride on a cleared line pushes that line's review back without moving its box. This is the pick for the next block (see Direction).

2. **The README says there is one predict-first question.** New. Small. `README.md:79` says "The first one is on Generic Line; more are coming." There are 19, three or more on every TypeScript line (`grep -c 'predict: "type"' src/data/typescript.ts`). The README is the first thing a visitor reads.

3. **Nothing keeps the predict-first questions in place.** New. This is the call ADR 0024 left open. Small. The bar leaves them out on purpose (`bar.ts`, the `choices()` calls). `data.test.ts` only checks their shape. So one edit could delete every predict-first question on a TypeScript line, and every test would still pass. That breaks the ratchet the bar exists for ([ADR 0005](../adr/0005-the-bar-as-a-test-ratchet.md)). See Direction for the options.

4. **The case study's numbers read as current but are from the tag.** New. Small. `CASE-STUDY.md:53` says "CI now runs ... 153 unit and content tests ... and two browser tests", and line 121 says the same. Today it is 161 tests and three browser tests. The fix is to say "at the tag" in both places or update the numbers. The first option is better, since the case study is a story told at 1.0.

5. **Every test run and build prints a Vite config warning.** New since the deploy commit. Small. `vite.config.ts:4` imports `./src/lib/securityHeaders` without a file extension, and Vite 8.3.5 warns that a future default config loader will not accept that. Nothing breaks today. The fix is to add the extension, as the warning says, then confirm the typecheck still passes. Or list it in `CLAUDE.md` next to the expected size warning, so nobody chases it.

6. **Two small doc drifts.** New. Trivial. The bundle item says "about 225 kB gzipped" (`ROADMAP.md:189`), and it is 238 kB now. `ARCHITECTURE.md:118` says the matcher compares a type as written when it has `=>`, `extends` or `?` outside brackets. The code also does this for `:`, `is`, `asserts` and `infer` (`predict.ts:78`). That is incomplete, not false.

Checked and fine, so no action:

- **The matcher never accepts a wrong answer.** From reading `predict.ts:30-113`, I could not find a guess it accepts that is a different type from the answer. Each matched member must be the same text as a member of the proven answer. Anything that binds looser than `|` (`=>`, conditional types, `is`, `asserts`) makes it fall back to comparing the whole text as written. A malformed guess can only match if its pieces are exactly the answer's well-formed pieces.
- **Running out of hearts with "I missed it" works.** `mark()` (`QuizGame.tsx:83`) reads `api.over` after scoring. That is a live getter on the ride (`PlayScreen.tsx`), not a stale value, so the run derails and does not also finish.
- **Typing a guess never triggers a shortcut.** `useKeys` ignores keys typed in an input, so a "1" in the guess box is never read as "I had it".

## Direction

### Should predict-first questions count toward the bar?

Three options:

1. **Leave them out entirely** (today). Costs nothing. But nothing protects 19 proven questions, and "done" says nothing about recall, which is the gap [ADR 0023](../adr/0023-predict-first-questions-after-1-0.md) named.
2. **Count them toward the pool sizes.** Small. But it lets a line reach its pool size with self-marked questions, and the TypeScript lines already clear without them, so it buys nothing.
3. **Keep them out of the counts, but require them.** Every line in a division that has adopted predict-first needs one at each tier: Local, Express and Rush Hour. Start with TypeScript only, which already meets it. Add React and NestJS when step 9 finishes them. Small: a list in `bar.ts`, one check in `auditLine()`, and one test.

**Recommendation: option 3.** It ratchets the work just done, matches what was built (one per tier on every line), keeps the old checks meaning what they meant, and does not fail React or NestJS before step 9. Record it in a short ADR, or as an amendment to ADR 0024.

### What comes next

I agree with predict-first as the block just finished. For the pick from Parked, the real fork is:

1. **The early-ride bug as a short block, then step 9.** Small to medium. One design call: compare `due` by calendar day, and let an early ride leave `due` alone. Doing both covers the 7pm-versus-8pm case and the "extra practice delays the review" case. It needs no save field, and a unit test in `engine.test.ts` can replay the first audit's 10-day example. It fixes Ryan's own review history, which gets worse every day he plays, and it removes the obvious follow-up to interview question 4.
2. **Step 9 straight away** (React and NestJS predict-first). Large: two new `predict` kinds, two matching rules, and probes in jsdom and Nest. It teaches the most new material, but the scheduling bug keeps compounding meanwhile.
3. **Split `App.tsx` first.** Medium to large. It makes the wiring testable, but no player would notice.

**Recommendation: option 1, then step 9.** Fold findings 2, 4, 5 and 6 into this inventory stop, since keeping docs true is part of closing it. Leave focus-after-screen-change parked, but it is the strongest candidate after step 9: predict-first added another place where focus lands on the page.

Nothing in this history is code Ryan wrote himself. That is by design ([ADR 0022](../adr/0022-nothing-waits-on-ryan-learning-the-code.md)), so `/audit quiz` and the case study carry "can he answer for it".

## Interview questions

1. **How does the app check a typed guess?** `predict.ts:13-36`, [ADR 0024](../adr/0024-how-a-predict-first-guess-is-checked.md). It splits the guess and the proven answer into tokens, ignores spacing, and compares the members of a top-level union in any order. If they do not match, the player sees both side by side and marks it, so a right answer written another way is never marked wrong.

2. **How do you know it never accepts a wrong answer?** `predict.ts:78-113`, `predict.test.ts`. Anything that makes reordering unsafe, like `=>`, `extends ... ?` or `is` outside brackets, makes it compare the text exactly as written. The tests hold 22 near misses that must stay unmatched, such as `string | number[]` against `(string | number)[]`.

3. **Why are questions a union type now?** `types.ts:32-66`. A `Question` is either a `ChoiceQuestion` or a `PredictQuestion`, and the `predict` field tells them apart. So the compiler makes any code that reads `opts` check the kind first, and `choices()` keeps the bar and the length checks to choice questions.

4. **How do reviews get scheduled?** `progression.ts:480-489`, with the gaps in `BOX_DAYS` in `save.ts`. Each line sits in a Leitner box, a step on a 1, 3, 7, 14, 30 day schedule, and an on-time review with at most one mistake moves it up a box. Be ready for the follow-up: an early ride resets the due date without moving the box, which is a known bug and the next fix.

5. **How does readiness work?** `progression.ts:166-184`. Each line gets a 0 to 1 score from the tier cleared, its place on the review schedule, and the share of its questions answered without a miss. It falls by up to half as a review goes overdue, so it shows what you would recall today. The weights (0.45, 0.2, 0.2, 0.15) still have no recorded reason.

6. **How did predict-first questions ship without breaking saves?** `save.ts:35`, `qid()` in `questions.ts`, [ADR 0015](../adr/0015-repair-damaged-saves.md). A question's history is keyed by its line and a hash of its text, whatever kind it is, so no new save field was needed. Had one been needed, it would get a default in `emptySave()` and a line in `migrate()`, or it would be dropped on the next load.

7. **How do you know a predict-first answer is right?** [ADR 0006](../adr/0006-prove-claims-by-running-them.md), `probes/ts/check.mjs`. Each answer is asserted as the exact type under TypeScript 5.9, 6.0 and 7.0, and a separate `neg-predict` file holds the tempting wrong guess and must fail to compile. CI runs all of them on every push, and a fact-checker that did not write the question reviews it.
